Case Study

SIAGA

An Indonesia-wide drought early-warning platform — turning XGBoost climate research into a live dashboard people can actually explore, not just a notebook and a paper.

Solo build · Full-stack platform + ML forecasting · View source on GitHub ↗ · Live Demo ↗

01 — The Problem

Climate research that only lives in a paper doesn't warn anyone

Research out of Universitas Negeri Semarang modeled how a specific, dated climate scenario — the "Godzilla El Niño 2026" — would affect drought risk across Indonesia, using spatio-temporal climate kinematics and an XGBoost forecasting model. That's valuable science, but a paper and a training notebook aren't something a policymaker, researcher, or the public can actually check. SIAGA's job was to turn that research into a product: a live dashboard where someone can see current drought risk, explore historical climate data back to 2000, and run their own "what if this year's El Niño is stronger or weaker" simulations — and to actually deploy it, not just demo it locally.

02 — What I Did

Built and deployed three connected pieces, solo

I built this alone, as three parts that had to ship together, not just run on my machine:

  • Training pipeline — feature engineering and model training on CHIRPS, MODIS, and NOAA OISST climate data (2000–2025), producing both a point-forecast XGBoost model and quantile models for Q10/Q50/Q90 prediction intervals, so the output is a range, not a false-precision single number.
  • Backend API — a FastAPI service serving six endpoints (metrics, historical data, forecasts, feature importance, island-level summaries, and real-time simulation), with JWT authentication and bcrypt password hashing gating the admin routes, and PyTest test files (test_api.py, test_auth.py) covering the API and auth logic.
  • Frontend dashboard — a React + Vite app using Recharts to visualize historical SDCI/ONI data, forecast projections, and SHAP-based feature importance, so the model's reasoning is inspectable, not a black box.

I also containerized the whole stack with Docker Compose and actually deployed it — backend on Railway, frontend on Vercel — instead of leaving "how to run this" as a local-only instruction.

03 — What Came of It

It's live, and I checked the numbers instead of just quoting the README

As of writing this, the dashboard, the API, and its Swagger docs are all reachable and responding — I hit them directly rather than trusting the README. I also called the live /api/metrics endpoint myself and got real evaluation numbers back: training R² of 0.985 (RMSE 0.014), but test R² of 0.737 (RMSE 0.050). That gap between training and test performance is a real signal of some overfitting on held-out data — worth naming honestly rather than only reporting the more flattering training number.

Where this project is further along than EcoSentra: it's actually deployed end-to-end and publicly reachable, and the admin routes have real JWT authentication instead of being wide open. Where it's a smaller system than EcoSentra: it's one model and one service, not a multi-service architecture with an agent-facing tool layer. Both are true at once, and I'd rather state the comparison than let either page imply it's the more "finished" project.

Stack & Reasoning

A few of the calls, and their trade-offs

TechnologyWhyTrade-off
XGBoostStrong performance on structured, feature-engineered climate data; supports both point forecasts and quantile intervalsLess suited to raw spatio-temporal imagery than a deep model — traded off in favor of engineered kinematic features
FastAPIAsync Python API that sits naturally next to the training pipelineA separate deploy target (Railway) to keep in sync with the frontend
React + ViteFast dev loop for an interactive, chart-heavy dashboardA second build/deploy pipeline (Vercel), separate from the Python backend
JWT + bcryptStateless auth for admin routes without running a session storeOnly admin routes are gated — the public dashboard has no user accounts, by design
Docker ComposeOne command to run backend + frontend together, matching production shapeA second "how to run this" path to keep in sync with the plain uvicorn / npm run dev instructions
